There are 230 open issues and PRs on the Bootstrap repository, a quarter of which are over three years old. Rewind a few months and we had over over 500. To help, we turned to LLMs and have had some amazing successes during the development of Bootstrap 6. The latest is an internal tool for us maintainers to triage everything automatically without prompting.

We vibe coded out `twbs/triage` to triage open Bootstrap issues and pull requests with an analysis, drafted responses, and when needed, a working fix prepared by agents. We maintainers still make every decision and post every response, but this has been helping us move faster and more efficiently.

Something we're most excited about is how personal software like this can be created so quickly, and then put to use in a way that benefits us and the community so immediately. Here's a look at our Triage tool in action.

## Keeping up

Bootstrap owes a lot to the many maintainers and contributors who have shaped it over the years. Today, the day-to-day work rests on two active core team members, [@mdo](https://github.com/mdo) and [myself](https://github.com/julien-deramond).

Over the last twelve months, we received 186 issues and 838 pull requests. Of those pull requests, 189 came from bots, 433 from the core team, and 216 from about 130 contributors. Of those 216, 60 were merged, 106 were closed without merging, and 50 are still open.

Answering any one of those well means reading the thread, checking against both v5 and v6 dev branches, looking for related work, reproducing the problem, and replying. As any maintainer knows, the biggest bottleneck is our time and attention.

## How it works

Earlier this month, I brought the setup I use to maintain my own projects into Bootstrap. I wrote more about that setup [on my personal blog](https://deramond.dev/blog/how-i-maintain-my-open-source-projects-with-claude-agents/).

I use Claude Code to sync our backlog and dispatch background agents. Their work lands in the Triage app. Every item follows the same five steps:

1. **Sync.** Read every open issue and pull request without writing to twbs/bootstrap.
2. **Analyze.** Read the thread, find related work, check both branches, and reproduce the problem.
3. **Prepare.** Draft the analysis, response, fixes, and next action.
4. **Store.** Save each item and its fix branches to twbs/triage.
5. **Decide.** Mark or I review the work, rewrite what needs rewriting, and act on GitHub by hand—or not at all.

Each issue or pull request gets a folder. [#37807](https://github.com/twbs/bootstrap/issues/37807), which asks for container queries in the flexbox grid, looks like this:

```text
issues/37807/
  analysis.md   what it is, findings, directions, recommendation
  answer.md     the status comment to post on the issue
  pr.md         fix 1: container-driven columns (recommended)
  pr-2.md       fix 2: the same, behind an opt-in Sass option
  meta.json     status, ease, related PRs, fix branches, dates
```

The analysis explains the item, what was checked, and what to do next. The answer is the exact text to post. Pull requests get a review covering the approach, CI, risks, and backports. Each item also gets a status—action, decision, waiting, or done—and an ease score:

- **9–10:** Paste the drafted comment and close, or merge.
- **6–8:** Submit a review, or open a pull request from a prepared branch.
- **3–5:** Check something by hand first.
- **0–2:** Make a real decision about scope, design, or a breaking change.

If the resolution needs code or docs, the agent prepares a fix branch from Bootstrap's own `main` or `v5-dev`. If there are multiple reasonable directions, it can prepare up to three so we can compare working code instead of hypotheticals.

The local dashboard puts all of this in one place, sorted by ease. It shows the next action, copies the drafted response, and compares prepared fixes with open pull requests.

## What changed

The key change we get from the Triage app is a clearer, actionable view of every open issue and pull request, allowing us to act faster with the right context. Within no time, agents had processed more than 200 remaining items and sorted them by what each needed next.

Now, when we have 20 minutes, we can pick an item, check the work, and act instead of spending that time rediscovering the problem, chasing histories across Git and GitHub cross references, etc.

The pass also exposed gaps in our GitHub labels. We standardized their names, documented every label, added missing labels like `bug` and `needs-decision`, and applied 410 labels across 198 open items. Agents can set factual labels from a fixed allowlist. Labels that imply a decision, like `duplicate` or `wont-fix`, still come from a maintainer.

We also added [GitHub Discussions](https://github.com/twbs/bootstrap/discussions) to our triage in-take. Instead of treating a long thread as one answered question, the analysis tracks each open point—bugs, feature requests, design questions, and support requests—back to the person who raised it.

## Hostile by default

Anyone can open an issue or pull request, so everything from them is treated as data, never instructions.

- Agents never check out, install, or run contributor code. They read the diff and use GitHub CI as evidence.
- They never open links from an issue. They build reproductions from scratch against Bootstrap's own `dist/`.
- They cannot comment, push, or open pull requests on twbs/bootstrap. Automatic labels from a fixed allowlist are the only exception.
- Anything suspicious stops for a maintainer to review by hand.

The agents also get things wrong. They don't know all of Bootstrap's history or the context that still lives in maintainers' heads. Sometimes they propose code where the right answer is to rethink the component. Their work is where we start, not what we ship.

This doesn't replace contributors, either. Prepared branches never copy an outside pull request. When a contributor has the right fix, the recommendation is to merge their work.

## If you contribute to Bootstrap

You'll see activity on old issues and pull requests in the coming weeks: fixes recognized, stale reports checked, and long-waiting pull requests reviewed. If we close something that shouldn't be closed, tell us in the thread.

You can help by:

- Providing a minimal reproduction with only Bootstrap's CSS and JavaScript, plus the version you're using.
- Targeting `v5-dev` for v5 fixes and `main` for new work. Since October 8, `main` is for v6 and `v5-dev` is for v5.
- Keeping each pull request to one change, with what it fixes and how you tested it.

The [contributing guidelines](https://github.com/twbs/bootstrap/blob/main/.github/CONTRIBUTING.md#issues-and-labels) explain what each label means. If you asked something in Discussions and never heard back, it's on our list now, too.

Questions and ideas are welcome in [GitHub Discussions](https://github.com/twbs/bootstrap/discussions). We'll report back in a few months with what worked and what didn't.
